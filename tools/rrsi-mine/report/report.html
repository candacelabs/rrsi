      Start here

      We turn past bug fixes from our own repository into an exam for an AI coding agent. An automatic process called RRSI then rewrites the agent's harness — the instructions, tools and step-by-step loop wrapped around the AI model, never the model itself — and keeps a change only when it raises the exam score by more than luck would. The final exam uses newer tasks the process never saw, so we can tell a real improvement from memorized answers.

      Like a driving test built from real incidents on your own roads. Every question is a situation that actually happened here, and we know a right answer exists because someone found it.
      Like a teacher who drills students on last year's homework, then grades them on this year's. If they only memorized last year's answers, this year's test shows it.

      The same pipeline works elsewhere. Another Go repository: only the repository path changes. A Python repository: pytest replaces go test; the rule “fails before the fix, passes after it” stays. A docs team: there are no tests, so a rubric grader (a checklist a reviewer or a model scores against) replaces them; mining past changes, the fairness checks and the newest-as-final-exam split stay the same.

        Words used on this page
        
  
        
    
        Task
        One past commit turned into one exam question: the code before the fix, a written instruction, and the commit's own tests as the hidden grader.
        
    
        Fix size
        Lines changed in the commit's reference fix: added plus removed lines in non-test, non-generated Go files. A one-line rename is 2 lines.
        
    
        Harness
        Everything around the model: e.g. a system prompt saying “run the tests before you submit”, the tools it may call, how many tries it gets.
        
    
        Practice set (evolve)
        The tasks RRSI may look at while it improves the harness — here, the  older exam-ready tasks.
        
    
        Final exam (held-out)
        Tasks kept aside until the end — here, the  newest exam-ready tasks.
        
    
        FAIL_TO_PASS
        The validity rule: a task counts only if its tests fail before the fix and pass after it — like the worked example above.
        
    
        BuildFail / TestFail
        How the tests failed before the fix: they did not compile (e.g. they call a function that does not exist yet), or they compiled and a check failed.
        
    
        Noise band
        How far the score moves when nothing changes: if the same harness scores 52% and then 56% on reruns, a 3-point “gain” means nothing.
        
    
        95% CI
        A range that would contain the true value in 95 of 100 repeated samples; with 10 tasks, ranges are wide.
